# گزارش بنچمارک production دانوآ — 2026-09-11

## محدوده آزمون

- Target: `https://danoa.ir`
- سناریو: ورود واقعی با API تایید OTP، بررسی session احراز‌شده و بارگذاری فهرست گفتگوها.
- 3,000 حساب تست برچسب‌دار با شناسه `loadtest-20260911-*` و شماره `0997000xxxx` در production ایجاد شد.
- برای جلوگیری از ارسال پیامک و هزینه، کدهای OTP داخلی یک‌بارمصرف در دیتابیس seed شدند. فراخوانی `send-verification-code`، چت، تولید تصویر و ویدیو اجرا نشد.
- توقف ایمن: error rate بیشتر از 2٪ یا p95 بیشتر از 3 ثانیه.

## وضعیت سرور

- 2 vCPU، 1.9GB RAM
- قبل از تست: 419MB swap استفاده شده و دیسک 87٪ پر بود (6.5GB آزاد)
- MySQL: `max_connections=151`، اما connection pool برنامه فقط 10 اتصال دارد؛ `Max_used_connections` در آزمون 12 بود.
- هنگام burst، CPU برنامه تا حدود 106٪ یک core مشاهده شد؛ سپس سرویس به حالت عادی برگشت.
- بعد از تست: app و MySQL هر دو healthy، `/healthz` برابر `ok`، و خطای جدید برنامه دیده نشد.

## برداشت عملی

- برای burst هم‌زمان این سه مسیر، 100 کاربر تاییدشده و قابل‌قبول است.
- 500 کاربر هم‌زمان برای این VPS و معماری فعلی قابل‌قبول نیست.
- ظرفیت دقیق بین 100 و 500 هنوز اندازه‌گیری نشده؛ برای production نباید بیش از 100 burst هم‌زمان را تضمین کرد.

## اقدام‌های پیشنهادی پیش از هدف 1,000+

1. ارتقای سرور به حداقل 4 vCPU و 8GB RAM، و آزادسازی دیسک تا زیر 70٪ مصرف.
2. اجرای دست‌کم دو replica از Node پشت Nginx و جداسازی MySQL از فرآیندهای application در صورت رشد.
3. تنظیم connection pool متناسب با replicaها و بررسی queryهای مسیر auth/conversations با slow-query monitoring.
4. اجرای دوبارهٔ load test با ramp تدریجی 150، 200، 300، 400 کاربر پس از تغییرات؛ سپس 1,000 و بالاتر در staging هم‌اندازه production.
